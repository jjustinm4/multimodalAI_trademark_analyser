# Trademark PoC — Build Prompt

Oct 24, 2026 · @justin

## System overview

A laptop-runnable PoC of the full trademark examination platform. No model training. Every matcher uses a pretrained model or a deterministic algorithm. The LLM is your local llama-server (`gpt-oss-20b-GGUF`) on port 8080. Synthetic data (fake trademarks, fake logos, fake TTAB decisions) is generated at first boot so the system works out of the box.

**What it IS**

- A Docker Compose stack: FastAPI backend, React frontend (Vite + nginx), PostgreSQL + pgvector
- llama-server runs on the host (GPU access); backend reaches it at `host.docker.internal:8080`
- ~5,000 synthetic trademarks with names, Nice classes, goods descriptions, and procedurally generated SVG logos
- All four conflict matchers (phonetic, semantic, visual, goods), a fusion scorer, Nice classification, absolute grounds screening, and RAG-grounded report drafting
- A React UI that looks and feels like a real examiner console: search, results with per-matcher score breakdown, and a generated examination report

**What it is NOT**

- Not production code — no auth, no RBAC, no rate limiting
- No fine-tuned models — semantic and visual matchers use off-the-shelf sentence-transformers and CLIP
- No LambdaMART fusion — uses configurable weighted averaging instead
- No real trademark data — everything is synthetic
- No examiner override logging or drift monitoring (governance layer is stubbed)

**Hardware assumptions**

- Ubuntu, 16GB+ RAM, NVIDIA GPU
- llama-server already installed and working (`llm` alias starts `gpt-oss-20b-GGUF` on port 8080)
- Docker and docker compose installed, NVIDIA Container Toolkit installed for GPU passthrough to embedding containers
- Working directory: `~/development/agentic_trademark_analyser`

## Architecture

**Services and ports**

| Service | Container name | Port | Role |
| --- | --- | --- | --- |
| FastAPI backend | `backend` | 8000 (mapped to host) | All API endpoints, matchers, embeddings, LLM calls |
| React frontend | `frontend` | 3000 (mapped to host) | Examiner console UI (Vite dev or nginx prod) |
| PostgreSQL + pgvector | `postgres` | 5432 (internal only) | Trademark records, vector indexes, precedent chunks |
| llama-server | HOST (not Docker) | 8080 | LLM inference for report drafting (OpenAI-compatible API) |

**Data flow for a query**

1. User types a mark name + goods description + optionally uploads a logo image into the React UI
2. Frontend `POST`s to `backend:8000/api/analyze`
3. Backend runs in parallel: phonetic matcher (jellyfish/rapidfuzz, no model), semantic matcher (sentence-transformers `all-MiniLM-L6-v2`, cosine vs pgvector index), visual matcher (CLIP `ViT-B/32`, cosine vs pgvector index — skipped if no logo), goods proximity (cosine similarity of goods embeddings)
4. Fusion scorer applies configurable weights to the four scores → ranked candidate list
5. Nice class suggester: embed query goods text, nearest-neighbour against pre-embedded ID Manual entries in pgvector
6. Absolute grounds screener: dictionary word check + prohibited terms list (rule-based)
7. Precedent retrieval: embed the query context, retrieve top-3 from fake TTAB chunks in pgvector
8. Report drafter: sends citations + grounds + precedent to llama-server at `host.docker.internal:8080/v1/chat/completions` with a structured system prompt → returns examination report
9. Backend returns JSON: `{citations: [...], nice_class: {...}, grounds: {...}, precedent: [...], report: "..."}`
10. Frontend renders the results dashboard: cited marks with score breakdowns, classification panel, grounds flags, and the generated report

**Embedding strategy (no training)**

- Text (mark names + goods descriptions): `all-MiniLM-L6-v2` from sentence-transformers, 384-dim vectors. Loaded once at backend startup, runs on GPU.
- Images (logos): `openai/clip-vit-base-patch32` from transformers, 512-dim vectors. Loaded once at backend startup, runs on GPU.
- Both indexes live in PostgreSQL via pgvector (HNSW index, cosine distance). Built at first boot from synthetic data.

**Network topology**

- `backend` and `frontend` share a Docker bridge network
- `backend` connects to `postgres` on the bridge network
- `backend` reaches llama-server on the host via `host.docker.internal:8080` (Docker's host gateway)
- `frontend` proxies `/api/*` to `backend:8000` (in dev: Vite proxy; in prod: nginx proxy_pass)

## Synthetic data specification

All data is generated by a Python script (`backend/seed.py`) that runs once at first boot. The script is deterministic (seeded random) so results are reproducible.

**5,000 synthetic trademarks**

Each record has: `id`, `mark_text`, `nice_class` (1–45), `goods_description`, `status` (registered / pending / opposed / dead), `owner_name`, `filing_date`, `logo_svg` (nullable), `text_embedding` (384-dim), `logo_embedding` (512-dim, nullable).

Generation rules:

- Mark names: combine syllables from a pool of ~200 (zen, tar, nova, tek, sol, plex, arc, lux, vex, ori, ...) into 2–3 syllable coined words. Deliberately inject clusters of similar names: for every 10th mark, generate 3–5 phonetic variants (swap z/s/x, double vowels, add/drop trailing vowels) to create realistic collision groups.
- Nice classes: distribute across all 45 with heavier weight on 9 (software), 25 (clothing), 35 (advertising), 42 (SaaS), 41 (education), 43 (food services).
- Goods descriptions: per-class template pools. Class 9: "software for {domain}", "mobile application for {purpose}", "downloadable electronic {thing}". Class 25: "{material} {garment}", "{style} {footwear}". 10–15 templates per class, domain/purpose/thing drawn from pools of ~30 words each.
- Owners: 500 fake company names from a combinator ("Apex", "Nova", "Stellar" + "Technologies", "Holdings", "Group", "Labs").
- Filing dates: random between 2015-01-01 and 2026-10-01.
- Status: 60% registered, 20% pending, 10% opposed, 10% dead.

**Logo SVGs (for ~2,000 of the 5,000 marks)**

Procedurally generated SVG strings: pick 1–3 geometric shapes (circle, triangle, rectangle, star, hexagon) in random colours, optionally overlay the mark text in a random font-weight. 200×200px viewBox. Stored as text in the database, embedded via CLIP at boot.

**200 fake TTAB decisions (for RAG)**

Each has: `proceeding_number` (fake format: "91XXXXXX"), `decision_date`, `mark_a`, `mark_b`, `outcome` (sustained / dismissed), `reasoning_text` (3–5 paragraph synthetic decision covering likelihood of confusion factors: similarity of marks, relatedness of goods, strength of senior mark, conditions of purchase). Generated from templates with variable substitution. Chunked into ~500-token passages and embedded at boot.

**69 Nice class reference entries (for classification)**

The 45 class headings from the Nice Classification plus 24 common sub-descriptions per high-frequency class. Each embedded at boot for nearest-neighbour classification.

**Prohibited terms list**

A hardcoded list of ~50 terms: national emblems ("United Nations", "Red Cross", "Olympic"), geographic indications ("Champagne", "Darjeeling", "Scotch"), scandalous terms, and government agency names. Used by the absolute grounds screener as exact and fuzzy match targets.

## Backend (FastAPI)

**API endpoints**

| Method | Path | Input | Output | What it does |
| --- | --- | --- | --- | --- |
| POST | `/api/analyze` | `{mark_text, goods_description, nice_class?, logo_file?}` | Full analysis JSON (citations, classification, grounds, precedent, report) | Runs the entire pipeline end-to-end |
| GET | `/api/search?q=zentara` | Query string | `{results: [{mark_text, nice_class, goods, status, similarity}]}` | Quick phonetic + semantic search only, no report |
| POST | `/api/classify` | `{goods_description}` | `{top_classes: [{class_number, class_name, confidence}]}` | Nice classification only |
| GET | `/api/marks` | Pagination params | Paginated list of all marks in the database | Browse / debug the synthetic corpus |
| GET | `/api/marks/:id` | Mark ID | Single mark record with all fields | Detail view |
| GET | `/api/health` | — | `{status: ok, llm: ok/unreachable, db: ok/unreachable}` | Healthcheck including LLM connectivity |

**Module: Phonetic matcher** (`matchers/phonetic.py`)

No model. Deterministic.

- Generate Double Metaphone + Soundex keys for the query mark using `jellyfish`
- Query PostgreSQL for all marks sharing any phonetic key (pre-computed at seed time, stored in a `phonetic_keys` JSONB column)
- Score each hit with `rapidfuzz.fuzz.ratio` (normalised edit distance) between query and candidate mark text
- Also compute Jaro-Winkler similarity via `jellyfish.jaro_winkler_similarity`
- Final phonetic score = max(fuzz_ratio, jaro_winkler), normalised to 0–1
- Return top-100 candidates with scores

**Module: Semantic matcher** (`matchers/semantic.py`)

Pretrained, no fine-tuning.

- At startup: load `sentence-transformers/all-MiniLM-L6-v2` onto GPU
- At query time: embed the query mark text → 384-dim vector
- pgvector query: `SELECT id, mark_text, 1 - (text_embedding <=> %s) AS similarity FROM marks ORDER BY text_embedding <=> %s LIMIT 100`
- The `<=>` operator is cosine distance; pgvector HNSW index makes this sub-second over 5K records
- Return top-100 candidates with cosine similarity scores

**Module: Visual matcher** (`matchers/visual.py`)

Pretrained CLIP, no fine-tuning.

- At startup: load `openai/clip-vit-base-patch32` (model + processor) onto GPU
- At query time: if a logo file is uploaded, encode it → 512-dim vector
- pgvector query: `SELECT id, mark_text, 1 - (logo_embedding <=> %s) AS similarity FROM marks WHERE logo_embedding IS NOT NULL ORDER BY logo_embedding <=> %s LIMIT 100`
- If no logo uploaded, this matcher returns an empty list and is excluded from fusion
- Return top-100 candidates with cosine similarity scores

**Module: Goods proximity** (`matchers/goods.py`)

Pretrained embeddings, no CrossEncoder training.

- Reuses the `all-MiniLM-L6-v2` model already loaded
- Embed the query goods description → 384-dim vector
- For each candidate from the other matchers (union of their results), compute cosine similarity between query goods embedding and candidate's pre-stored goods embedding
- This is a re-scoring step, not a search step — it only scores candidates already surfaced by phonetic/semantic/visual
- Return a goods_proximity score (0–1) per candidate

**Module: Fusion scorer** (`matchers/fusion.py`)

No LambdaMART. Configurable weighted average.

- Default weights: `{phonetic: 0.30, semantic: 0.30, visual: 0.20, goods: 0.20}`
- If no logo (visual matcher skipped): redistribute visual weight proportionally → `{phonetic: 0.375, semantic: 0.375, goods: 0.25}`
- Union all candidates from all matchers, fill missing scores with 0.0
- `final_score = sum(weight_i * score_i)`
- Sort descending, return top-25
- Weights are configurable via environment variables so they can be tuned without code changes

**Module: Nice classifier** (`classifier/nice.py`)

Pretrained embeddings, nearest-neighbour.

- At seed time: embed all 45 Nice class headings + 24 sub-descriptions using `all-MiniLM-L6-v2`, store in pgvector
- At query time: embed the query goods description, find top-3 nearest class entries
- Return `[{class_number, class_name, confidence (cosine similarity)}]`

**Module: Absolute grounds screener** (`screener/grounds.py`)

Rule-based. No model.

- **Descriptiveness check**: tokenise the mark text, check each token against the English dictionary (`nltk.corpus.wordnet`). If ≥50% of tokens are common English words and the mark is ≥2 words, flag as potentially descriptive.
- **Prohibited terms**: fuzzy match (`rapidfuzz.process.extract`) the mark text against the prohibited terms list. Threshold: 85% similarity → flag.
- **Single-letter / numerals**: flag marks that are a single character or purely numeric.
- Return `{descriptive: bool, prohibited_match: str?, flags: [str]}`

**Module: Precedent retrieval** (`rag/retrieval.py`)

Pretrained embeddings + pgvector search.

- At seed time: chunk 200 fake TTAB decisions into ~500-token passages, embed with `all-MiniLM-L6-v2`, store in pgvector table `precedent_chunks`
- At query time: construct a retrieval query from the mark text + top cited mark + goods description
- pgvector nearest-neighbour search → top-3 chunks
- Return `[{proceeding_number, decision_date, excerpt, similarity}]`

**Module: Report drafter** (`drafter/report.py`)

llama-server via OpenAI-compatible API.

- Construct a system prompt that instructs the LLM to produce a structured examination report citing only the provided evidence
- User message contains: the query mark, its class, cited prior marks (top 3–5 from fusion), grounds screening results, and retrieved precedent passages
- Call `POST http://host.docker.internal:8080/v1/chat/completions` with `model: "gpt-oss-20b"`, `max_tokens: 2000`, `temperature: 0.3`
- Parse the response and return the report text
- If llama-server is unreachable, return a fallback template-based report (no LLM) with a warning banner

**Startup sequence (backend)**

1. Wait for PostgreSQL to be ready (retry loop)
2. Run Alembic migrations (create tables with pgvector extension)
3. Check if marks table is empty → if yes, run `seed.py` (generate synthetic data, compute all embeddings, insert into PostgreSQL with pgvector indexes)
4. Load ML models into GPU memory (`all-MiniLM-L6-v2`, CLIP)
5. Start uvicorn on port 8000

**Key libraries**

`fastapi`, `uvicorn`, `sqlalchemy`, `asyncpg`, `pgvector` (Python bindings), `sentence-transformers`, `transformers`, `torch`, `Pillow`, `jellyfish`, `rapidfuzz`, `nltk`, `httpx` (async HTTP client for llama-server), `pydantic`

## Frontend (React + Vite)

**Stack**: React 18, Vite, TailwindCSS, React Router, Axios. No component library — Tailwind utility classes only.

**Pages and routes**

| Route | Page | What it shows |
| --- | --- | --- |
| `/` | Search | The main input: mark name (required), goods description (required), optional logo upload (drag-drop zone), optional Nice class override dropdown. A prominent "Analyze" button. Below: a "Quick Search" toggle for phonetic+semantic only (no report). |
| `/results/:id` | Results Dashboard | The full examination output. Five panels described below. |
| `/browse` | Corpus Browser | Paginated table of all 5,000 synthetic marks with search/filter. Click a row to see its detail. For demo and debug. |

**Results Dashboard panels** (rendered after `/api/analyze` returns)

1. **Header bar**: query mark name, class badge, risk level badge (HIGH / MEDIUM / LOW based on top citation score: >0.8 HIGH, 0.5–0.8 MEDIUM, <0.5 LOW), timestamp.
2. **Citations panel** (left, main): a ranked list of cited prior marks. Each card shows: rank number, mark name, Nice class badge, status badge (registered/pending/opposed/dead), overall score (large, coloured), and a horizontal stacked bar showing the four matcher contributions (phonetic: blue, semantic: purple, visual: green, goods: orange). If a logo exists for the cited mark, show the SVG thumbnail. Clicking a card expands it to show the raw score per matcher.
3. **Classification panel** (right sidebar, top): the top-3 suggested Nice classes with confidence bars. If the user provided a class, show whether it matches the top suggestion (green check or amber warning).
4. **Grounds panel** (right sidebar, middle): absolute grounds flags. Green "clear" badges for checks that passed, red alert badges for anything flagged (descriptive, prohibited, single-letter). Each flag shows the evidence (e.g. which prohibited term matched, which tokens are dictionary words).
5. **Report panel** (full width, bottom): the LLM-generated examination report rendered as formatted text. A subtle "Generated by AI — review before signing" banner at the top. A "Copy to clipboard" button.

**UI behaviour**

- On submit, show a skeleton loading state with progress messages: "Running phonetic analysis...", "Computing semantic similarity...", "Retrieving precedent...", "Drafting report..." (timed, not real — the backend returns all at once, but the frontend simulates sequential progress for the demo feel).
- Logo upload: accept PNG, JPG, SVG. Show preview. Convert to base64 and send in the POST body.
- Responsive: works on 1920px and 1366px widths. Not mobile (examiners use desktops).
- Dark/light mode via Tailwind `dark:` classes, default to system preference.

## Startup sequence

What happens when you run `docker compose up --build` for the first time:

1. Docker builds the backend image (CUDA 12.1 base, installs Python deps including PyTorch, sentence-transformers, transformers, CLIP). This takes 5–8 minutes on first build; cached afterwards.
2. Docker builds the frontend image (npm install, Vite build, copies dist to nginx). Takes ~1 minute.
3. PostgreSQL container starts, creates the `trademark` database, runs healthcheck.
4. Backend container starts once Postgres is healthy:
   1. Runs Alembic migrations: creates `marks` table (with pgvector `text_embedding vector(384)` and `logo_embedding vector(512)` columns, plus `phonetic_keys jsonb`), `precedent_chunks` table, `nice_classes` table.
   2. Enables pgvector extension: `CREATE EXTENSION IF NOT EXISTS vector`.
   3. Creates HNSW indexes: `CREATE INDEX ON marks USING hnsw (text_embedding vector_cosine_ops)` and same for `logo_embedding`.
   4. Checks if `marks` table is empty → if yes, runs `seed.py`.
   5. `seed.py` execution (3–5 minutes on first boot with GPU):
      - Loads `all-MiniLM-L6-v2` and CLIP `ViT-B/32` onto GPU
      - Generates 5,000 synthetic marks (names, classes, goods, owners, dates, statuses)
      - Generates SVG logos for ~2,000 of them
      - Computes text embeddings (384-dim) for all 5,000 mark names
      - Computes text embeddings for all 5,000 goods descriptions
      - Computes CLIP embeddings (512-dim) for the ~2,000 SVG logos (renders SVG to PIL Image first)
      - Computes phonetic keys (Double Metaphone + Soundex) for all 5,000 mark names
      - Generates 69 Nice class reference entries and embeds them
      - Generates 200 fake TTAB decisions, chunks them, embeds chunks
      - Bulk inserts everything into PostgreSQL
      - Prints: "Seeded 5000 marks, 2000 logos, 200 decisions, 69 class refs"
   6. Loads ML models into GPU memory for inference (reuses the ones from seeding)
   7. Starts uvicorn on 0.0.0.0:8000
   8. Prints: "Backend ready — models loaded, 5000 marks indexed"
5. Frontend container starts, nginx serves the built React app on port 80 (mapped to host 3000).
6. nginx proxies `/api/*` requests to `backend:8000` on the Docker bridge network.

**On subsequent boots** (data already seeded): steps 4.4–4.5 are skipped. Backend goes straight from migrations to model loading. Startup takes ~30 seconds.

**If llama-server is not running**: everything works except the report drafter, which returns a fallback template report with a yellow banner. The health endpoint reports `llm: unreachable`.
